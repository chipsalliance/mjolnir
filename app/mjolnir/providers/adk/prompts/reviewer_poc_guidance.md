## Proof-of-Concept (PoC) Authenticity & Execution Verification

When a finding includes a synthesized Proof-of-Concept (`poc`), ground-truth sandbox patch, and `run_harness_command` execution log from the `poc_creation` phase, you MUST audit the PoC's authenticity and execution proof before issuing your final verdict:

1. **Zero Production Code Modification:** Inspect the ground-truth sandbox patch. Verify that the patch ONLY adds or modifies test/harness code (and build targets if needed) and does NOT alter, weaken, or comment out production logic, validation checks, or struct definitions in the target module. If the PoC modifies production code to force a failure, reject the PoC immediately.
2. **Non-Triviality & Target Fidelity:** Verify that the test invokes the real production function under audit with concrete inputs matching `attack_vector`, and does NOT rely on vacuous assertions or mocked target logic.
3. **Public Interface & Caller Precondition Fidelity:** Verify whether the PoC drives the component's public/exported entry point or uses unit-test symbol visibility to invoke a private/internal helper directly. In firmware and systems code, internal helpers often rely on bounds checks or state validations performed by their public caller. If the PoC calls an internal helper directly and the public entry point blocks or sanitizes that input, you MUST reject the PoC and classify the finding as `FALSE_POSITIVE` (or `NOT_EXPLOITABLE` if unreachable in production lifecycle states).
4. **Build Profile & Environment Fidelity:** Check whether the PoC relies on host-test-only compiler semantics (such as debug-only arithmetic traps or assertions that are disabled in the target's production firmware/release build profile, or non-security bringup/unprovisioned lifecycles where authentication is intentionally bypassed). If production build semantics do not lead to memory corruption, out-of-bounds access, denial of service, or authentication/logic bypass, classify the finding as `NOT_EXPLOITABLE` (`LOW` / `INFORMATIONAL`).
5. **Causal Execution Proof (When `poc_verified` is `True`):** Inspect the captured `run_harness_command` execution output and exit code. Confirm that the test compiled and executed cleanly and that its runtime behavior causally proves a real security violation.
6. **Preserving Hardware, Side-Channel & Harness-Limited Vulnerabilities (When `poc_verified` is `False`):** NEVER close (`FALSE_POSITIVE`) or dismiss a genuine code flaw solely because `poc_verified` is `False` or because no dynamic unit test could be executed. Distinguish strictly between:
   - **`[HARNESS_LIMITATION]` (Keep `OPEN`):** If `poc_verified` is `False` because the flaw involves hardware/MMIO/CSR/OTP/ePMP registers, DMA/interrupt concurrency, target-only RISC-V assembly, physical power/EM/timing side-channels (`CWE-208`), fault-injection hardening (`HARDENED_TRY` / `launder32`), or build/simulator environment constraints, preserve the finding as `OPEN`. However, calibrate the verdict and severity accurately according to the attack boundary:
     - For **pure physical fault-injection or glitching vulnerabilities** without physical silicon execution proof, classify as `OPEN` with `HARDENING_REQUIRED` / `DEFENSE_IN_DEPTH` justification, reflecting defense-in-depth importance without conflating it with an immediately exploitable remote software CVE.
     - For **software-reachable logic or bounds flaws** that only hit harness limitations due to simulator/register mocking constraints, evaluate the static caller chain and rate exploitability based on production API reachability.
   - **`[DISPROVED_BY_HARNESS]` (Close as `FALSE_POSITIVE` / `NOT_EXPLOITABLE`):** Close a finding with `poc_verified = False` ONLY when the PoC attempt uncovered a concrete code guard, bounds check, or public caller invariant that genuinely prevents exploitation in production.
7. **Verdict & Justification Calibration:** Incorporate your PoC authenticity, public API reachability, and hardware/harness limitation assessment directly into your final `verdict`, `severity`, and `justification`. Calibrate CVSS v3.1 metrics (`cvss_score`, `cvss_vector`), classify the root silicon security objective violation (`security_objective_violation`), and require structured MITRE `cwe` mapping in the finding summary.
